## 七、报告模板（以此为准）

以实际报告 `RCP-10910-2-sit代码评审报告-2026-08-12-09-47-22.md` 为最佳范本，结构固定，逐节输出。

### 7.1 总体结构

```markdown
# <需求编号> <项目名> <阶段分支> 代码评审报告

- **评审时间** / **评审人** / **评审对象**（仓库列表 + 分支 + 提交备注标识 + 聚合评审说明）
- **需求文档**：<编号>《<名称>》<版本>
- **提交人**：<Git 实际作者列表>

## 〇、本次复评基线说明（重要）        ← 复评必写；首轮可省略
1. 需求基线：新版本需求与旧版差异比对 → 业务规则是否变化
2. 代码基线：重新拉取 <branch>，列出最新 <requirement_id> 提交 hash；分支新增非本需求提交是否触碰本需求涉及文件（git diff 校验）
3. 结论：问题项与上版一致性、总数变化

## 一、评审范围与方法
- 1.1 覆盖的提交（表：仓库 / 提交数 / 时间跨度 / 主要提交人）
- 1.2 评审方法（聚合净变更；**逐文件 git diff 全覆盖，禁止主观跳过任何文件（含生成代码）**；其它需求改动如何剔除；问题条目标注规范）
- 1.3 需求要点（对照用）：逐条列需求条款要点（编号+一句）
- 1.4 数据库验证（仅涉及 SQL 时）：验证环境（SIT/UAT，按分支）、涉及 SQL 文件、已验证项、未验证项（STG/权限不足）

## 二、问题清单（按严重程度排序）
> 图例：🔴=高（需求符合性/正确性）🟠=中（健壮性/一致性）🟡=低（质量/规范）。
> 【新】=本轮新增；其余标注状态。
<逐条问题，格式见 7.2>

## 三、已修复项（告知团队）           ← 复评对比上版
## 四、跨仓库一致性问题（重点确认）
## 五、责任分派建议（表：开发者 / 待处理问题；特殊专项单列小节）
## 六、共性规范建议（提交粒度 / 幂等去重 / 判空 / 需求口径拉通 / 跨仓对齐等）
## 七、建议修改顺序（先改 / 次改 / 顺手）
## 八、排除项（非本需求代码，已剔除）← 区间内混入其它需求时必写
## 九、变动文件清单（本需求最终版本净变更涉及的每个文件）
> 字段：序号 / 变更类型（A=新增，M=修改，D=删除）/ 文件路径 / 变更内容概述。取自 `git log --name-status` 逐文件核对；**必须逐文件全覆盖**，禁止凭主观跳过生成代码类文件。
> 表：| 序号 | 变更 | 文件路径 | 变更内容概述 |
## 十、提交记录清单（本需求全部 Git 提交，完整列出）
> 字段：序号 / Git 提交编号 / 提交注释 / 提交人 / 提交时间。取自 `git log --format="%h|%an|%ad|%s"`，**按新→旧排列（新提交在上，与 git log / IDEA 提交记录一致）**——排序按提交图拓扑/提交时间倒序，时间列显示作者时间 `%ad`（作者时间与图序倒挂时按图序，不改动）；提交人取 Git 实际作者，禁止用提交注释里的 `--user`。
> 表：| 序号 | 提交编号 | 提交注释 | 提交人 | 提交时间 |
```

### 7.2 单条问题条目格式（以 example-report.md 范本为准，逐字段对齐）

```markdown
### 🔴 L-01 需求4.2：<问题一句话>（未修复 / 已修复 / 待确认）

> **说明**（可选）：术语澄清、该问题同时存在于多库等提示。

- **类/文件**：<仓库> `<完整类路径或 mapper>:<行号>`（跨库/多文件时用列表列出）
- **调用链**：
  ```
  第427行  createFixedAmountConBenifit("NB", ...)   ← 新单投保录入场景入口
  第588行  private String dealTimeUnitOfFixAmntBenifit(...)   ← 问题所在
  第590-595行  NB 分支：只读 planDetail.getAMNTUNIT()
  ```
  （每行：行号 + 方法(...) + `←` 场景/问题标注；问题所在行标 `← 问题所在`）
- **需求条款**：<章节> —— <需求原文要点（尽量引原文）>
- **问题代码原文**（标注问题行，❌ 指向缺陷，✅ 标注正常对照）：
  ```java | sql | xml
  ...示例代码...                        // ❌ 缺陷点说明
  ...示例代码...                        // ✅ 正确做法/对照
  ```
- **问题**（多角度分点，可选）：1. xxx；2. xxx；3. xxx
- **对照**（跨库/跨场景实现差异，可选）：legacy `...` 如何、nbx `...` 如何 → 口径不一致说明
- **性能证据**（仅性能问题）：SQL + 执行计划或索引/统计信息 + 实测行数与耗时
- **具体故障场景**：<编号步骤：数据前提 → 触发 → 错误结果/后果>
  1. 数据前提：xxx；
  2. 触发：xxx；
  3. 错误结果：xxx → 后果。
- **责任人**：<Git 实际作者>（`<hash>`；多提交用 `/` 分隔，注明各自引入/修复）
- **建议**：<具体改法及修复后行为>
```

### 7.3 编号与符号约定

- 问题编号按仓库缩写前缀约定，由项目自行定义：`<前缀>-<序号>`，编号随严重度排序递增，复评新增号追加在尾。示例：CGIS 用 `L`=legacy、`N`=nbx、`B`=nb。
- 严重级别：🔴=高（BLOCKER/CRITICAL，需求符合性/正确性）、🟠=中（MAJOR，健壮性/一致性）、🟡=低（MINOR，质量/规范）。
- 状态标注：`未修复` / `已修复`（含修复内容+提交，可附 `**遗留**` 列剩余问题）/ `待确认`（需需求方/架构确认）。
- 问题条目字段必含：标题（级别+编号+需求章节+状态）、类/文件、调用链、需求条款、问题代码原文（❌标注）、具体故障场景（编号步骤）、责任人、建议。`问题`/`对照`/`说明` 按需补充。
