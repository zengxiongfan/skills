# 代码评审方法规范（通用）

> 用途：作为大模型执行代码评审的输入规范，适用于任意项目、任意需求。
> 核心方法：**将本需求全部提交聚合为最终版本净变更，再审最终版本，问题逐项归因到需求提交。**

## 〇、输入参数（评审前必须确认，缺一不可，不得猜测）

评审开始前先明确以下参数；未提供时先向用户确认，不得自行猜测：

| 参数 | 含义 | 示例 |
|------|------|------|
| `requirement_id` | 需求标识，用于筛选提交 | `RCP-10910-2` |
| `branch` | 评审分支（远端） | `feature-JIRA-RCP10910-2` |
| `repos` | 仓库列表（单仓即一个，多仓逐一评审） | `cgis-legacy-app`、`cgis-web-nbx` |
| `requirement_doc` | 需求文档路径（建立规则台账的依据） | `福利树项目文档/需求文档.../...v0.12.md` |

聚合区间、文件白名单均由提交自动推导（见「二」），无需额外参数。

> **项目配置示例（CGIS）**：`repos` = 10 个服务——`cgis-legacy-app` / `cgis-web-nbx` / `cgis-web-nb` / `cgis-web-claim` / `cgis-web-ruleclm` / `cgis-web-benefit` / `cgis-front-gemini` / `cgis-web-policy` / `cgis-web-system` / `cgis-web-gateway`；提交筛选标识格式 `RCP-XXXX`；问题编号前缀见 `project-config-cgis.md`。其他项目按实际覆盖。

## 一、范围界定

1. 每个仓库独立评审；多仓项目逐一评审，范围 = 需求提交涉及的所有仓库（单仓项目即一个仓库，见输入参数 `<repos>`）。
2. 只审**远端**分支 `<branch>`（评审分支）：先 `git fetch origin <branch>`，失败即停止，不得用本地旧引用继续。
3. 以提交说明是否含完整需求标识 `<requirement_id>` 筛出需求提交；**只审这些提交引入的代码**，不得混入其他需求或他人代码。
4. 禁止用整分支 diff 作为评审范围（可能混入同分支其他需求代码）；范围只能来自需求提交聚合（见「二」）。

## 二、变更聚合（核心）

5. 圈定需求提交：`git log <branch> --grep="<requirement_id>"` 列出本需求全部提交，只审这些提交引入的代码。
6. 聚合区间 = **最早需求提交的父节点 → 最新需求提交**（`<最早>^..<最新>`）；对该区间做 diff，得到本需求最终版本净变更——中间反复（bug 修复、乱码调整等）全部折叠，只评最终形态。
7. diff 必须加**文件白名单**：`git log --grep="<requirement_id>" --name-only | sort -u` 得到需求涉及文件清单，diff 时用 `-- <文件清单>` 限定，防止区间内其它需求对同文件的改动被误并。
8. **逐文件 git diff 全覆盖（强制，禁止主观跳过）**：对白名单内**每一个**文件逐一执行 `git diff <最早>^ <最新> -- <单个文件>` 并审查。禁止凭文件名、扩展名、"看起来只是生成代码"等任何主观理由跳过文件；MBG 生成的 schema/model/db/vdb 类同样要 diff，确认字段同步完整、`FIELDNUM` 等编号一致。**文件清单必须从 diff 结果自动汇总**（`git log --name-status` 逐个文件核对 A/M/D 与提交归属），禁止凭记忆手工汇总，防止漏写。
9. 逐文件核对区间内提交归属：`git log <最早>^..<最新> -- <文件> | grep -v "<requirement_id>"`；凡出现非本需求提交的改动，从评审中剔除并列入报告"排除项"。
10. 评审对象是**最终版本**文件；只报告最终版本仍存在的问题，中间提交已修复的问题不报；若区间内同一文件被多需求反复交叉改动、或历史非线性导致纯 diff 失真，退而按"每个文件的最终提交链"单独审。

## 三、归因

11. 提交人取 Git 实际作者 `git log --format="%an"`，**禁止**用提交说明里的 `--user` 字段；禁止按"文件提交次数最多"推断责任人。
12. 问题逐项归因：`git blame -L` 定位最终问题行的最后修改提交，再验证该提交属于需求提交集合（`git log -S` 复核）。
13. 最终版本已不存在、或非本需求提交引入的问题，**不得报告**。

## 四、审查执行

14. 先完整读需求文档，建立**需求规则台账**（规则ID / 来源章节 / 适用范围 / 处理规则 / 预期结果 / 边界与例外），再逐条对照最终实现。
15. 必须验证**行为结果**（正常/反向/空值/边界/组合条件/状态流转），不能只查代码里是否出现需求字段、常量或提示文字。
16. 从需求规则与代码改动**双向追踪业务链路**，拉通跨文件、跨服务实现，核对输入、枚举、默认值、精度、状态语义是否一致。
17. 基础代码问题开放审查：正确性（NPE/越界/类型/状态/精度/并发）、安全（SQL注入/越权/XSS）、可靠（异常/事务/幂等/资源/部分失败）、数据一致性、接口契约、性能、可维护（死代码/魔法值/过时注释）；维度只是视角，按实际链路继续发现清单之外的问题。
18. 需求矛盾、缺口径或引用材料不可用：**不得自行选一种解释认定代码有错**，标记"需求待确认/核验受限"，与代码缺陷分开统计。

## 四·补、数据库验证（涉及新增/修改 SQL 时）

- 仅对白名单内新增/修改的 SQL（Mapper XML、注解 SQL、拼接 SQL、DB 脚本）执行；纯 Java/前端改动跳过。
- 按 SQL 所属服务选择 schema（见 `CGIS服务知识库/数据库与Schema映射.md`），只在该 schema 验证，不跨 schema 猜。
- 静态核对表/列存在性、类型长度、约束、索引与统计信息；只读试跑 SELECT，DML 改写成等价 SELECT 验证影响行数。
- 执行计划：对 SQL 执行 `EXPLAIN PLAN FOR <SQL>`（不带 `STATEMENT_ID`，会写 `PLAN_TABLE`），再执行 `SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY())` 读取计划；无权限或 PLAN_TABLE 不可用时退化为索引/统计信息 + 实测行数耗时，并标注「执行计划不可得」。
- 性能问题按全表扫描、索引失效（函数/隐式转换/前导 `%LIKE`/`OR`/`NOT IN`）、复合索引列序、回表、子查询基数、分页、N+1、批量提交等维度分析，归入「基础代码问题-性能」。
- dbx 可查 SIT、UAT；STG 分支只做静态分析并标注「未做运行验证」；SIT/UAT 数据量不代表生产，性能结论为参考值；按分支选环境，不混用。

## 五、严重级别

19. BLOCKER（必改，系统不可用/严重数据损坏）/ CRITICAL（影响正确性/可利用漏洞）/ MAJOR（部分功能或可靠性、性能）/ MINOR（可验证的维护性问题）。结合触发条件、影响范围、可恢复性判定，**不按类型机械定级**。

## 六、问题条目与报告

20. 每个问题固定字段：service / category（需求一致性|基础代码问题）/ requirementRule / file / line（最终版本行号或范围）/ developer / commit / commitTime / severity / issue / evidence / fix。
21. `issue`：什么问题 → 什么后果 → 什么触发条件；`fix`：具体改法 → 改后行为；`evidence`：最终版本仍存在 + 属于本需求提交的验证依据。
22. 报告附**提交记录清单**（完整列出本需求全部提交，字段：序号 / Git 提交编号 / 提交注释 / 提交人 / 提交时间，取自 `git log --format="%h|%an|%ad|%s"`，**按新→旧排列**——新提交在上，与 git log / IDEA 提交记录一致；排序按提交图拓扑/提交时间倒序，时间列显示作者时间 `%ad`）。报告附**变动文件清单**（字段：序号 / 变更类型[A新增|M修改|D删除] / 文件路径 / 变更内容概述，取自 `git log --name-status` 逐文件核对）。
