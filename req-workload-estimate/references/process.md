# 完整流程细节（req-workload-estimate reference）

> SKILL.md 是流程骨架与硬规则；本文是各阶段的完整细节，含两级回源触发矩阵与产物清单。

## Skill 定位

- **输入**：需求文档（docx/doc/xlsx/pdf）、工作量评估模板.xlsx、代码仓库（明确基线分支）
- **输出**：改造点清单（技术版）+ 工作量评估表（含需求原文双向追溯）+ 生成脚本与 tasks.json + 版本留痕
- **总流程**：六个阶段 + 一个评审循环。评审循环是常态（实践中可达 10 轮），每轮"查证 → 修正 → 出新版本"。

---

## 阶段 0：需求文档解析（调用 req-doc2md 技能）

### 0.1 转换（标准动作，不手工解析）
调用 req-doc2md 把需求文档转成 md，产出：
```
{filename}.md                        ← 阅读入口
{filename}_files/
  ├── images/                        ← 截图
  ├── attachments/                   ← 附件（Excel/Word 均为带样式的原始文件）+ 伴生 .md
  ├── tables/                        ← 表格 CSV/JSON + table_index.json
  ├── 样式标注.md                     ← 正文颜色/高亮/下划线/批注/修订索引（有则生成）
  ├── styles.json                    ← 同上，机器可读
  ├── report.json                    ← 机器可读：status/checks/warnings/errors
  ├── 转换报告.md                     ← 人读对账
  ├── manifest.json                  ← 章节/表格/附件/图片总清单
  ├── outline.md                     ← 章节树 + 行号范围
  └── attachment_index.json          ← 附件索引
```

### 0.2 先读质量门和样式旁车（顺序固定）
1. **读 report.json / 转换报告.md**：status 必须 green。出现 warning/failed（未识别嵌入对象 / 批注未提取 / 格式信息未覆盖 / 表格数不一致）→ 立即回原始 docx 排查，不带病进入后续阶段。
2. **读 样式标注.md**：掌握哪些文字带格式语义（如"标红=调整点""橙色=待确认"），以及批注/修订内容。

### 0.3 再读正文与附件
md 正文 → 附件 md → 截图（理解 UI 语境、字段名、页面布局）。

### 0.4 格式语义处理规则——两级回源 + 触发矩阵

**一级回源（轻量，常规路径，不碰 docx）：**

| 场景 | 检测方式 | 动作 |
|---|---|---|
| S1 正文引用视觉属性，信息在**附件内部**（如"调整点见清单内标红的内容"） | 关键词扫描：标红/红色/标黄/高亮/加粗/颜色/红字/如上图/见下图/截图/批注/修订（读 md 时做） | openpyxl 直接解析 `attachments/` **原始 xlsx** 的字体颜色/填充，**不凭 md 下结论** |
| S2 正文引用视觉属性，信息在**正文自身** | 同上 → 查 样式标注.md | 索引已列出全部带格式文字，通常到此为止；**索引与正文引用对不上（说"标红"但索引无红色条目）= 矛盾信号，升级二级** |

**二级回源（重量，解原始 docx）——仅 4 个触发场景：**

| 触发 | 检测来源 |
|---|---|
| T1 转换报告 ⚠：嵌入对象未识别 / 有 comments.xml 但批注提取为空 / 有格式文字但样式标注未生成 | 转换报告.md 自动对账（读报告即知，不带病往下走） |
| T2 产物为旧版（无 转换报告.md / 样式标注.md，即优化前的存量产物） | 文件不存在即知 → **优先用 req-doc2md 重转**；不能重转才手工回源 |
| T3 语义矛盾且一级回源解释不了：清单"现状=调整后"却声称有调整点、附件原件里也找不到区分维度；截图与正文矛盾 | skill 侧语义自洽检查（转换器不懂语义） |
| T4 转换过程报错 / 附件提取失败（stdout 出现"处理失败"） | 脚本输出 |

**二级回源的手工取证手法**（T2 无法重转、或 T1/T3 需要实锤时）：
解压读 `document.xml` 全文（含页眉页脚脚注）；标红等附件内样式从 `word/embeddings/*.bin`（OLE2 复合文档 → package 流 → OOXML 包）解析 `styles.xml` 红色字体 → `cellXfs` 映射 → 单元格样式比对还原；用"现状描述 ≠ 调整后展示规则"的差异单元格交叉验证。

**四层检测在新流程中的去向**（检测没有消失，是重新分工）：
- 第 1 层（文本信号）→ 保留 skill 侧，命中后先走一级回源，不再直奔 docx；
- 第 2 层（结构对账）→ **被 转换报告.md 自动化**，skill 只需"读报告看绿不绿"；
- 第 3 层（语义自洽）→ 保留 skill 侧（转换器不懂语义）；
- 第 4 层（兜底默认）→ 保留但降级："引用视觉属性即默认不可信"不变，默认回源对象从"解 docx"降为"附件原件"，解 docx 是最后手段。

### 0.5 原文瑕疵记录（不擅改）
错别字（如"何龙部分金额"实为"合理部分金额"）、字段名前后不一致、截图与正文矛盾——引用原文时保留原样并加〔〕标注。

### 0.6 需求条款编号化
如 §4.1.2 调整后①②③④、§4.2.1-1（否/是）、§4.3.2-1~3，后续所有评估点都挂这些编号。

**产出**：编号化需求条款清单 + 格式语义索引 + 对账结论。

## 阶段 1：代码定位与现状核实

1. **知识库只用于定位**，结论必须落到源码（以代码为准）。
2. **并行探索**：多路 Explore 子代理分别定位前端页面 / 后端保存与累计逻辑 / 查询接口，各自给出"功能点 → 文件:行号"映射。
3. **关键点亲自复核**：影响工作量的代码（"强制置为是"类元凶逻辑、字段联动）直接读到行，不信转述。
4. **编码陷阱**：源码 GBK，`iconv` 必须加 `-c`（否则静默截断，实测 586 行文件只转出 400 行）；grep 结果交叉验证。
5. **核实"现状"**：原文描述 vs 代码行为，不符要记录为待对齐项。
6. **识别多副本/多路径**（漏一处就是一个缺陷）：
   - 审核区/审批区两套控件（`_SH`/`_SP` 类命名）；
   - 同一逻辑的多处副本（保存/回退/复核/审批等入口）；
   - 多条计算/展示路径（如 新理算 / GHB 旧理算 / NGB 旧理算）；
   - 同源复制页面（协谈调整、在途质检、赔案详情等）；
   - legacy 老核心排查（即使零命中也要做，作为排除证据）。
7. **基线确认**：评估基线分支（如 origin/sit，注意本地与远端一致性），检查相关功能是否在基线上、是否由其他需求/项目并行交付。

**产出**：代码落点映射 + 现状证据 + 多副本清单 + 基线结论。

## 阶段 2：改造点拆分

每个改造点四要素（缺一不可）：需求原文引用（原文摘录，不转述）、现状（代码证据：文件:行号）、改造内容、落点（前端/后端/涉及文件）。

1. 按需求章节组织任务分类（A/B/C/D…）。
2. 标注前提与口径问题（基线分支、并行交付、共用页面、业务线限定）。
3. 列**待确认项**：所有影响工作量口径的开放问题单独列出，附证据与建议，交用户拍板。
4. 产出**技术版清单**（改造点清单.md）：保留代码落点作为自证依据；附"需求原文 ↔ 改造点"对应索引。

**产出**：改造点清单.md（技术版）。**先出清单评审，确认后才进入定值。**

---

## 阶段 3：口径澄清（与用户/业务交互）

- 每条待确认项：证据 + 建议 → 用户拍板 → **记录销项结论**。
- **需求没说的 → 不做，但记录剔除依据**（实例：下游链路经核查是测试重点非开发；同类页面需求未列示不处理）。
- **需求说了的 → 查原文依据再补**（实例：GHB 旧理算路径依据 §4.1/§4.2 标题业务线限定；审批区依据 §4.1.1 功能位置列示）。
- 回答"需求有没有说 X"必须**全文关键词检索**（正文 + 页眉页脚 + 内嵌工作簿），零命中才下"没说"结论。
- **历史数据问题三分类**：开发改造 / 测试回归重点 / 运维修数——分别对应是否计入开发工作量。

**产出**：已销项清单 + 剔除依据 + 备案项。

## 阶段 4：评估表生成

1. **对齐模板**：先读模板 xlsx 的列结构、字体、列宽、合并规则、行高，确认与脚本内置格式一致。
2. **列设计**：序号 / 任务分类 / 子任务 / 任务事项 / 管理 / 需求 / 设计 / 开发工作量(人/天) / 测试工作量 + **对应需求原文点**（新增列）；管理/需求/设计/测试为分类级字段（仅块首行填写），按任务分类块纵向合并；开发工作量逐行填写、不合并。四列留空时脚本自动补全：取该任务分类开发小计的 1/5，向上取整到 0.5（尾数 0.1~0.5 含 0.5 取 0.5，大于 0.5 向上取 1），显式填写优先，顶层 `"auto_estimate": false` 可关闭。
3. **描述规范（对外业务语言）**：禁代码类名称（类/文件/方法/表/字段/SQL）；用功能表述替代；代码落点留在技术版清单。
4. **双向追溯**：Sheet1 每行带"对应需求原文点"（含〔对照现状〕〔依据〕〔现状核验备注〕标注）；Sheet2 反查表：需求原文点 → 开发序号（支持一对多）。
5. **备注区**：口径说明（含/不含什么）、剔除依据、测试重点提示、待业务对齐项、依据文档。
6. **脚本化生成**：写 tasks.json → `python scripts/gen_estimate.py tasks.json -o 输出.xlsx`；改数值/条目改 JSON 重跑，不手改 xlsx。
7. **版本纪律**：每次改动出新版本文件（v2/v3/…），绝不覆盖旧版；目标文件被 Excel 占用（`~$` 锁 / PermissionError）→ 输出新文件名并告知。
8. **自检**：脚本内置正则扫描（驼峰、文件后缀、全大写标识、SQL 关键字）；再复读生成的 xlsx 校验内容、合并区、合计。
9. **标准实施费用模板（可选双产出）**：`standard_template.enabled=true` 时，`gen_estimate.py` 自动调用 `gen_std_template.py`，额外生成 `..._标准模板_vN.xlsx`（7 阶段）。规则：管理/需求/设计/开发/测试五段分别对齐 10 列对应列小计；设计/测试镜像开发任务分类并排除 `self_test_category`（默认“开发联调与回归自测”）；测试另加固定用例编写 2 天；验收默认 5、版本默认 1/1/1；费率默认 1846/1846/1261/1261/1030/1261/1261；从零构建，写入 WPS `KSOReadingLayout=true`。10 列的“设计/测试”列自动补全同样排除自测分类，保证两表五列对齐。
10. **输出命名**：不传 `-o` 时按原始需求文档名自动命名——去掉扩展名、尾部“需求规格说明书vX”和版本号，拼 `-工作量评估`；版本 `_vN` 扫描目录自动递增（同时看 10 列与标准模板文件），可用 `--version`/`--outdir` 指定；`--doc` 优先于 tasks.json `source_doc`，显式 `-o` 优先级最高。

**产出**：工作量评估 xlsx（评估表 + 反查表）+（可选）标准实施费用模板 xlsx + tasks.json + 生成脚本。

## 阶段 5：核对审计（评审循环核心）

1. **双向核对**：需求条款逐条 ↔ 评估点；反查表保证无孤儿。
2. **多余检测**：脚本逐场景 diff 清单"现状 vs 调整后"——无差异且无标红即无实质改造，识别重复计量（实例：已结案展示规则与新增列/累计规则重复）。
3. **用户质疑 → 先查证再回答**：不盲从也不硬顶（实例：查到下游早有 `!"0".equals()` 判断 → 确认剔除"下游影响"开发项）。
4. **连带影响判断**：规则变更的下游消费方逐个核实"是否已有支持"，区分"要改代码"与"只需回归"。
5. 每轮修正后：更新反查表序号映射 → 重跑脚本与自检 → 出新版本。

**产出**：核对结论（遗漏/多余清单）+ 修正后的新版本。

## 阶段 6：定值与口径分层

1. **锚定模板惯例**：参考模板中同类任务的人天量级。
2. **代码体量取证**：`wc -l` 量出改造涉及文件总行数——这类遗留系统"改动量小、理解量大"。
3. **逐条定值并给理由**：不整体乘系数；偏紧条目单独说明（"6,510 行文件 + 4 处副本 + 老问题"）。
4. **口径分层（显式声明，写进备注）**：
   - **开发工作量**（不含需求澄清、方案评审、测试用例、系统测试）——评估表口径；
   - **纯人力 vs AI 辅助**：纯人力上浮约 1.3 倍（理解成本、GBK 编码陷阱、多副本遗漏风险）；
   - **完整交付**：开发工作量 +30~50%（测试等）。
5. **条件项处理**：范围待确认条目单列，备注"不含则合计为 X"。

**产出**：定值表 + 口径说明。
