# 坑清单（req-workload-estimate reference）

> 实战教训。每条都真实踩过，代价已付过一次，别再付第二次。

## 需求文档侧

1. **md 转换有损是机制性的**：GFM 无颜色语法 + 附件曾按纯值重生成（req-doc2md 保留附件原件）。样式语义永远以 样式标注.md / 附件原件为准，**不凭 md 下结论**。
2. **旧版转换产物没有旁车文件**（无 样式标注.md / 转换报告.md）→ 优先用 req-doc2md 重转，别直接手工解 OLE。
3. **需求原文错别字**（如"何龙部分金额"实为"合理部分金额"）：引用时保留原样加〔〕标注，**不替业务改**——评估表要能对回原文。
4. **"需求现状描述"与代码实际行为不符**（原文说"支持查询并编辑"，代码实际"隐藏并重置为是"）：记录为待对齐项，**不擅自按任何一方实现**，验收口径让业务拍板。
5. **截图与正文矛盾**（正文写"默认为否"、截图是"全部"）→ 说明有信息要回原始载体核对，别忽略。

## 代码侧

6. **GBK 源码 + `iconv` 不加 `-c` 会静默截断**：实测 586 行的 mapper 只转出 400 行，**186 行 SQL 直接看不见**。读 GBK 文件永远加 `-c`。
7. **grep 结果不稳定**：同一文件，raw grep 与转码后 grep 命中数可能不一致；工作区级批量 grep 尤其不可靠 → 关键结论换一种方式再验一遍。
8. **多副本是缺陷之源**：审核区/审批区两套控件、保存/回退/复核/审批多处同逻辑副本、新理算/GHB/NGB 多条路径、同源复制页面——**漏掉任何一处就是一个缺陷**，逐个列清单核对。
9. **legacy 老核心要排查并留证**：即使零命中也要做（"零命中"本身就是"老核心不需要改"的证据）。

## 工具与脚本侧

10. **Excel 打开着目标文件 → PermissionError**：目录里出现 `~$xxx.xlsx` 锁文件即说明被占用 → 输出新版本文件名，**不要试图杀 Excel**。
11. **脚本内嵌长中文备注，引号可能被转成全角**（`"` → `“`）→ Python 语法错误。备注用**字符串列表 + join** 重写，别用超长内联字符串。
12. **req-doc2md 输出目录默认是 docx 所在目录**：测试时用 `-o` 指定输出目录，避免误更新工作区产物。
13. **合计行不要塞需求章节清单**：与反查表（Sheet2）重复且不准确——合计行只放合计数。

## 评估口径侧

14. **AI 读代码速度远快于人类 → 估值天然偏低**：纯人力口径需显式上浮（约 1.3 倍），理由是理解成本、编码陷阱、多副本遗漏风险；逐条给理由，不整体乘系数。
15. **口径必须显式声明**：开发工作量（不含测试/澄清）≠ 完整交付（+30~50% 测试等）≠ 纯人力口径——三个数别混着报。
16. **用户质疑先查证再回答**：查代码、查原文，零命中才说"没说"。既不盲从（"好好好我删"）也不硬顶（"肯定要算"）。
17. **需求没说的不做，但要留剔除依据**：写进备注（"经核查不涉及开发改造，原因……"），免得日后有人问"为什么没算这块"。
18. **历史数据问题三分类**：开发改造 / 测试回归重点 / 运维修数。落库值（如保额累计）才可能涉及修数；实时计算的值（如已用福利）改规则即追溯生效，不需要修数但要业务知情。
