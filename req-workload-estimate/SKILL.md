# req-workload-estimate 需求工作量评估

**输入**：需求文档（docx/doc/xlsx/pdf）+ 代码仓库（先确认基线分支）+ 工作量评估模板.xlsx
**输出**：改造点清单（技术版 .md）→ 工作量评估表（.xlsx，含需求原文双向追溯）→ 生成脚本与 JSON → 版本留痕

## 流程总览

```
阶段0 需求解析(req-doc2md) → 阶段1 代码定位 → 阶段2 改造点拆分 → 阶段3 口径澄清
     → 阶段4 评估表生成 →（评审循环：阶段5 核对审计 → 修正 → 新版本）→ 阶段6 定值与口径分层
```

**铁律：先出改造点清单给用户评审，确认划分与范围后，才进入定值出人天表。**

评审循环是常态：用户会多轮反馈（保留/删除/改口径/质疑），每轮都走"查证 → 修正 → 出新版本"，**绝不覆盖旧版**。

---

## 阶段 0：需求文档解析（调用 req-doc2md 技能）

1. **第一步永远是 req-doc2md 转换**，产出 md（阅读入口）+ `_files/`（images、attachments 带样式原件、tables CSV/JSON、样式标注.md、styles.json、report.json、转换报告.md、manifest.json、outline.md）。
2. **先读 report.json / 转换报告.md，再读正文**：status 必须 green（OLE、表格、合并单元格、批注、修订、格式对账）。出现 warning/failed → 先排查，不带病往下走。
3. **读 样式标注.md**：掌握哪些文字带格式语义（"标红=调整点"）、批注、修订。
4. 然后读 md 正文 → 附件 md → 截图。
5. **格式语义两级回源**（详见 references/process.md 的触发矩阵）：
   - 一级（常规）：正文引用视觉属性（标红/高亮/如上图…）且信息在**附件内部** → 直接用 openpyxl 解析 `attachments/` **原始 xlsx** 的字体颜色，**不凭 md 下结论**；信息在正文自身 → 查 样式标注.md。
   - 二级（兜底，仅 4 场景）：转换报告 ⚠ / 旧版产物无法重转 / 语义矛盾一级解释不了 / 转换报错 → 回原始 docx 取证（解压 document.xml、解内嵌 OLE、解析 styles.xml）。
6. **原文瑕疵不擅改**：错别字、字段名前后不一致、截图与正文矛盾——引用时保留原样加〔〕标注。
7. **需求条款编号化**（如 §4.1.2 调整后①②③④、§4.2.1-1（否/是）），后续所有评估点都挂这些编号。

## 阶段 1：代码定位与现状核实

1. **知识库只用于定位，结论必须落到源码 文件:行号**（知识库是快照，以代码为准）。
2. **并行探索**：多路 Explore 子代理分别定位前端页面 / 后端保存与累计逻辑 / 查询接口。
3. **关键点亲自复核**：影响工作量的代码（元凶逻辑、字段联动）直接读到行，不信子代理转述。
4. **编码陷阱**：源码 GBK，`iconv` 必须加 `-c`（否则静默截断）；grep 结果要交叉验证。
5. **核实"现状"**：需求描述的现状 vs 代码实际行为，不符 → 记录为待对齐项，不擅自按任何一方实现。
6. **识别多副本/多路径**（漏一处就是一个缺陷）：审核区/审批区两套控件、同一逻辑多处副本、多条计算/展示路径、同源复制页面、legacy 老核心排查（零命中也是排除证据）。
7. **基线确认**：评估基线分支（如 origin/sit），检查相关功能是否在基线上、是否由其他需求/项目并行交付。

## 阶段 2：改造点拆分（产出技术版清单）

每个改造点四要素，缺一不可：
- **需求原文引用**（原文摘录，不转述）
- **现状**（代码证据：文件:行号）
- **改造内容**
- **落点**（前端/后端/涉及文件）

按需求章节组织任务分类（A/B/C/D…）；**待确认项**（所有影响工作量口径的开放问题）单独列出，附证据与建议交用户拍板。产出 `改造点清单.md`（技术版，保留代码落点作自证依据）+ 需求原文↔改造点对应索引。

## 阶段 3：口径澄清（用户拍板）

- 每条待确认项：证据 + 建议 → 用户定 → **记录销项结论**。
- **需求没说的 → 不做，但记录剔除依据**（如：下游链路经核查是测试重点非开发）。
- **需求说了的 → 查原文依据再补**（标题业务线限定、功能位置列示都算依据）。
- 回答"需求有没有说 X"必须**全文关键词检索**（正文+页眉页脚+内嵌工作簿），零命中才下"没说"结论。
- **历史数据问题三分类**：开发改造 / 测试回归重点 / 运维修数——分别对应是否计入开发工作量。

## 阶段 4：评估表生成（用脚本）

1. 先读工作量评估模板.xlsx 的列结构/字体/列宽/合并规则，确认与脚本内置格式一致（模板六列：序号/任务分类/子任务/任务事项/开发工作量(人/天) + 新增"对应需求原文点"）。
2. **描述用业务语言，禁代码类名称**（类/文件/方法/表/字段/SQL）——用"审核结论区、审批结论区两处联动""全链路开发"这类表述；代码落点留在技术版清单。
3. 写 `tasks.json`（结构见下），运行脚本生成，**不手改 xlsx**：
   ```bash
   python <skill_dir>/scripts/gen_estimate.py tasks.json -o 工作量评估_需求名.xlsx
   ```
4. 脚本自动做：任务分类纵向合并、合计行、备注行、Sheet2 反查表（需求原文点→开发序号，支持一对多）、**代码类名称自检**（命中会打印告警，改 JSON 重跑）。
5. **版本纪律**：每次改动出新版本文件（v2/v3/…），绝不覆盖旧版；目标文件被 Excel 占用（`~$` 锁 / PermissionError）→ 输出新文件名并告知用户。
6. 备注区必备内容：口径说明（含/不含什么）、剔除依据、测试重点提示、待业务对齐项、依据文档。

**tasks.json 结构**（`--example` 可打印样例）：
```json
{
  "title": "【需求名】工作量评估",
  "tasks": [{"no":1, "category":"任务分类（同类留空合并）", "subtask":"子任务",
             "item":"任务事项（业务语言）", "days":2, "source":"§章节号+原文摘录"}],
  "reverse": [{"point":"§4.1.1", "summary":"原文摘要", "tasks":"5；4〔依据〕"}],
  "notes": ["1、……"]
}
```

## 阶段 5：核对审计（评审循环核心）

1. **双向核对**：需求条款逐条 ↔ 评估点；反查表保证无孤儿（有评估点没原文、有原文没评估点都要能解释）。
2. **多余检测**：脚本逐场景 diff 清单"现状 vs 调整后"——无差异且无标红即无实质改造，识别重复计量。
3. **用户质疑 → 先查证再回答**：查代码、查原文，不盲从也不硬顶（实例：查到下游早有标志位判断 → 确认剔除该开发项）。
4. 连带影响逐个核实"是否已有支持"，区分"要改代码"与"只需回归"。
5. 每轮修正：更新反查表序号映射 → 重跑脚本与自检 → 出新版本。

## 阶段 6：定值与口径分层

1. **锚定模板惯例**：参考模板中同类任务的人天量级。
2. **代码体量取证**：`wc -l` 量出改造涉及文件总行数——遗留系统"改动量小、理解量大"。
3. **逐条定值并给理由**，不整体乘系数；偏紧条目单独说明（如"6,510 行文件 + 4 处副本 + 老问题"）。
4. **口径分层显式声明**（写进备注）：
   - 开发工作量（不含需求澄清、方案评审、测试用例、系统测试）——评估表口径；
   - 纯人力 vs AI 辅助：纯人力上浮约 1.3 倍（理解成本、GBK 陷阱、多副本遗漏风险）；
   - 完整交付：开发工作量 +30~50%（测试等）。
5. **条件项**：范围待确认条目单列，备注注明"不含则合计为 X"。

## 硬规则（必须遵守）

1. 先出改造点清单评审，确认后才出人天表。
2. 第一步 req-doc2md 转换；先读 report.json / 转换报告.md，status 必须 green，再读正文。
3. 格式语义默认不在 md 里：正文引用视觉属性且信息在附件内部 → 解析附件原始 xlsx，不凭 md 下结论。
4. 回源分两级：常规=附件原件/样式标注；解原始 docx 仅 4 场景（对账⚠/旧版无法重转/语义矛盾/转换报错）。
5. 知识库只定位，结论验证源码。
6. GBK 用 `iconv -c`；grep 交叉验证。
7. 每个评估点双向挂需求原文（正向任务→原文，反向原文→任务）。
8. 对外交付禁代码类名称；代码落点留技术版清单。
9. 需求没说的不做，但记剔除依据；需求说了的查原文再补。
10. 用户质疑先查证，零命中才说"没说"。
11. 版本纪律：新版本文件，不覆盖旧版；Excel 占用输出新名。
12. 脚本化生成 + 自检，不手改 xlsx。
13. 工作量分层口径显式声明。
14. 历史数据问题三分类：开发改造 / 测试重点 / 运维修数。
