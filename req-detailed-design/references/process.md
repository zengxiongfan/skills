# 完整流程细节（req-detailed-design reference）

> SKILL.md 是流程骨架与硬规则；本文件是阶段 0-7 的完整动作、命令配方、agent 分派模板与评审循环规范。

## 阶段 0：需求解析

### 0.1 转换（标准动作）

调用 req-doc2md 技能把需求文档转成 md 包：

```
<name>.md + <name>_files/
  images/  attachments/（OLE 原件+伴随 md+样式 json）  tables/（csv/json）
  样式标注.md  styles.json  report.json  转换报告.md  manifest.json  outline.md
```

**顺序固定**：先读 `report.json` / `转换报告.md`（status 必须 green，warning 先排查）；再读 `样式标注.md`（标红/高亮/批注/修订）；然后正文 → 附件 md → 截图。

### 0.2 docx 批注必提取

批注常在正文之外给出关键指引（例："本次章节可参考'社保使用情况'的处理 RCP-14939"——这直接决定了参照实现与两阶段设计模式）。提取方法：

```bash
cd /tmp && mkdir -p docx_x && cd docx_x
unzip -o -q <docx> -d extracted
python - <<'PY'
import re
xml = open('extracted/word/comments.xml', encoding='utf-8').read()
for author, date, body in re.findall(r'<w:comment [^>]*w:author="([^"]*)"[^>]*w:date="([^"]*)"[^>]*>(.*?)</w:comment>', xml, re.S):
    print(author, date, ''.join(re.findall(r'<w:t[^>]*>([^<]*)</w:t>', body)))
PY
```

### 0.3 多版本需求必 diff

同一需求有 v0.1/v0.2/v0.4 时：

```bash
diff <旧版.md> <新版.md>
```

- 产出「版本变更清单」（修订记录表 + 正文 diff + 附件新增），逐条决定：设计文档哪章修订、哪些附录计数变化；
- **不重写全篇**：只改受影响章节，其余保留；文档头追加版本块；
- 附件/正文矛盾（如字段值域表格写 Y/N、示例报文写 1/0）→ 记录两处出处进"待确认"，不擅自统一。

### 0.4 内嵌 OLE 附件（定稿来源）

接口字段说明、参数表等常以 OLE 附件内嵌，是 SA/业务定稿来源。req-doc2md 已产出 `attachments/{att}.md` + 原件；**附件 md 表达不全时（表格丢失）解 docx 的 `document.xml` 提取全文**：

```bash
python - <<'PY'
import re, zipfile
xml = zipfile.ZipFile('<att>.docx').read('word/document.xml').decode('utf-8')
print(''.join(re.findall(r'<w:t[^>]*>([^<]*)</w:t>', xml)))
PY
```

## 阶段 1：基线确认

### 1.1 配方（各仓 origin/sit worktree）

```bash
cd <workspace>
for r in repo1 repo2 repo3; do
  cd $r
  git fetch origin sit --quiet
  if [ -d "../_sit_worktrees/$r" ]; then
    git -C "../_sit_worktrees/$r" checkout --detach origin/sit --quiet
  else
    git worktree add --detach "../_sit_worktrees/$r" origin/sit --quiet
  fi
  echo "$r origin/sit=$(git rev-parse --short origin/sit)"
  cd ..
done
```

### 1.2 漂移核对（评估基线 vs 当前基线）

```bash
cd <repo>
git diff --name-only <评估基线sha>..origin/sit -- <相关路径>
```

- 漂移文件 → 阶段 3 重点重核（行号可能偏移），在改造点定位中标注"评估 :起 → 当前 :起，+N"；
- 漂移清单同时决定文档头基线表（repo@sha，全列）。

### 1.3 门禁

worktree 全部就绪 + 漂移清单输出 + 文档头基线表可填 → 才进入阶段 2。

## 阶段 2：改造点承接与范围界定

1. 读改造点清单（req-workload-estimate 产物）：按需求章节映射为「章节 → 改造点编号（A1/B1/…）→ 落点文件」承接表。
2. **显式声明不改范围**：需求原文的排除项（GHB/报表/老页面/测试验证节/规则待定节）逐条写进文档头与对应章节；改造点清单里"不计开发"的项同样声明。
3. **继承并复核待确认项**：清单里的待确认项逐条带到设计文档 C.1；清单结论已过时的（如"后端未实现"经 git 追溯实为已实现）在正文标注"与清单不符，已核实"。
4. **清单行号/路径视为待核**：评估行号普遍可能偏大或路径错误（实例：`AIOUpCommoVo` 实际在 `claim/vo/`），一律以当前基线重核。
5. 若清单缺失：先按需求章节自行拆改造点（每点给"需求原文/现状/改造内容/落点"），经用户确认后再进入代码核查。

## 阶段 3：并行代码核查

### 3.1 分组原则

按**业务块**分 5-6 组（不是按仓库分），避免交叉：示例分组——①接口推送+账单后端；②账单+I 类前端；③福利树（前后端）；④理算（ruleclm+claim）；⑤权限控制（多服务）；⑥编码配置+SQL 参照。

### 3.2 agent prompt 固定四段

```
你是代码核查员。任务：为 <需求号> 详细设计提取「<分组名>」改造点的精确代码上下文。只读代码，唯一允许写的文件是 <素材路径>。

【环境】
- worktree：<绝对路径>（= 最新 origin/sit@<sha>，<日期>）
- ⚠️ 编码实测：Java 多 GBK（必须 `sed -n 'X,Yp' <file> | iconv -f GBK -t UTF-8 -c`；grep 加 -a）；Mapper XML/前端多 UTF-8（可直接读）。编码以 file 实测为准。
- 评估基线 <sha>，行号可能漂移，以当前 worktree 为准并标注漂移。

【改造点与评估时定位】
<逐条：编号 + 描述 + 文件路径/方法/评估行号 + 参照查询>

【输出契约】写入 <素材路径>，每个定位点一节：
### <编号> <文件短名> <方法/SQL>
- 文件完整相对路径
- 当前行号（评估行号→当前行号，漂移量）
- 代码块：插入点/参照点前后各5行原代码（转码后 UTF-8，带行号，标注行号范围）
- 该处业务语义一句话
- 若评估定位漂移或找不到，写明实际情况

最后返回：每个文件的漂移汇总 + 与评估不符之处摘要。素材文件要完整，返回消息只需摘要。
```

### 3.3 组长亲核清单（不信转述）

- 元凶逻辑（匹配分支/判定入口/公共方法签名）；
- 全列 update 语句（新增列是否在**语句末尾**）；
- 跨服务调用链（feign 入参/返回 BO 能否承接新字段）；
- SQL 口径（与参照 SQL 逐条件对照）；
- 既有硬编码/联动（如医院编码末位=2 的三处覆盖——新字段是否被误联动）。

### 3.4 素材验收

每个改造点必须拿到「当前行号 + 前后 5 行 + 语义」三件套；缺一补一；agent 找不到的锚点，组长亲自按"类名+方法名+原文行"重定位后补发任务。

## 阶段 4：设计决策与跨参照复核

### 4.1 语义取证四步（禁止想当然）

1. 找字段/码值的**全部用法**（grep 调用方、SQL 过滤、DDL/DML 注释）；
2. 找**最贴近的参照实现**（需求点名的 JIRA、既有同族逻辑）；
3. 用**数据/DDL 证据**定语义（如 `lcbill.premtype`：`BillManageSql.properties` 里 '1' 配子团体、'2' 配被保险人、'0' 配投保人 → 是账单层级，不是首续期）；
4. 结论写进 0.2 全局约定表；拿不准的进 C.1。

### 4.2 参照实现逐环节比对

把参照链路拆成固定环节：`配置入口 → 保存落库 → 因子注册 → 一阶段匹配 → 二阶段校验 → 置位 → 传递(feign) → 持久化(全列/选择性 update) → 清零 → 查询(规则/报表) → 展示(页面)`；新设计逐环节给出对应实现与差异说明。差异处是最容易漏改的地方（实例：参照实现的标志在 `updateByPrimaryKey` 语句**末尾**，只抄选择性 update 就漏了）。

### 4.3 闭环验证

每个新增标志/字段回答 6 问：谁置位？怎么传？落哪张表哪条语句？何时清零？谁查询？哪里展示？——写成一节「闭环说明」或逐点注释；答不出的进待确认。

### 4.4 多调用方/多副本排查清单

- 因子/字段清单是否有**第二调用方**（通用匹配之外：预授权累计、默认规则判定、报表）；
- 主表+日志表是否**成对加列**，日志写入是否 insert-select **显式列清单**（漏加=快照恒 NULL）；
- 页面是否双份（普通/GHB）、查询是否双路径（含缓存分支）、前端是否双入口（审核/审批）；
- 同一规则的多处硬编码副本（如医院编码联动三处）。

### 4.5 公共方法与失败隔离

- 同一业务规则被 ≥2 个消费方使用 → 抽公共方法（服务类），各消费方只负责"取数+组装+调用+聚合"；
- 判定逻辑有 SQL 版第二实现（规则引擎 RULESQL）时，明确"口径须与公共方法一致，改规则三处同步"；
- 附加能力（标识/提示）不得拖垮主流程：调用链设计为失败隔离（try-catch 默认值 + 主流程照常返回），或专用接口（失败只影响自身）。

### 4.6 跨服务边界

- 不在本工作区的服务（接口聚合服务/契约服务/厂商）、外部系统字段值域 → 列 SA/协作依赖，不假设其行为；
- 他人先行的交付（另一个需求先上线提供的字段/DDL）→ 写清"谁交付、是否先行、本需求只做上线前核对与阻断条件"。

## 阶段 5：文档撰写

1. 先填文档头（基线表/版本块）→ 0 章总表 → 0.1 Mermaid → 0.2 四张表；
2. 按需求章节逐章写：需求要点（原文编号化）→ 文件清单 → 后端（定位+代码块+说明）→ 前端 → 自测；
3. **代码块一律用 `extract_context.py` 生成**（单点或 `--tasks` 批量），粘贴后人工加注释前缀行；
4. 每写完一章，核对本章文件清单与附录 D 草稿一致；
5. 最后写附录 A/B/C/D + 上线顺序；跑「交付前自检 12 项」；
6. 写作期间**不凭记忆写代码**：所有原文以素材/当前基线为准；变换类改动必须两端可对应。

## 阶段 6：评审循环

1. 用户反馈（改口径/加校验/换落点/删范围）→ **先查证**（查代码、查需求原文/附件）再回答；不盲从也不硬顶；
2. 每轮修订：改正文 → 改附录计数 → 追加版本块（V1.x 变更摘要）→ 自检；
3. **撤销方案留痕**：相关章节保留一行「曾评估 X 方案，已撤销（原因）」（实例：insuredPolicy 方案撤销）；全文旧引用 grep 清零；
4. 用户拍板的口径：C.1 条目移入 C.2（C.1 留 `~~原条目~~ 已销项` 一行）；
5. 需求又发新版：回到阶段 0.3（diff→增量更新→版本块），不重写全篇。

## 阶段 7：交付与沉淀

### 7.1 交付摘要（回复用户的最后一节必须包含）

- 文档路径 + 行数/版本；
- 本次改了什么（按章节/版本）；
- 待确认 N 条 + 需协作 M 件（点名）；
- 给开发的一句话口径（规则写在哪、改规则要同步哪几处）。

### 7.2 素材与记忆

- 核查素材目录保留（agent 产出），供后续版本修订复用；
- 关键事实（他人需求归属、字段语义更正、落点变更）写项目记忆，避免下轮重复踩坑。
