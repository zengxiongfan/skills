# 设计文档模板契约（req-detailed-design）

> 本文件把「RCP-10910 式详细设计方案」的骨架固化为可复用契约。写文档前通读一遍；产出必须满足本契约与文末「交付前自检 12 项」。

## 一、文档头（模板）

```markdown
# <需求号> <需求名> — 详细设计方案（按需求章节划分）

> **文档性质**：开发实现级设计文档（可复制粘贴代码直接开发）
> **需求来源**：《<需求文档名>》**<版本>**（修订记录摘要：初版日期 / 各版变更点）
> **组织方式**：**按需求文档章节划分（4.1~4.9）**，每章明确"涉及代码文件 + 改造点 + 可粘贴代码"
> **核心语义**：一句话点出本需求的语义变更（字段/规则/开关/数据流）
> **不改范围**：显式列出不做的部分及需求依据（如 GHB 不涉及/报表不改/老页面不改/测试验证节不开发）
> **版本**：V<主>.<次>（<日期>）
> **V<版本> 变更（对应需求 <版本>）**：①…；②…（逐版追加，旧版摘要保留）
> **代码基线**（<核对日期> 核对，均为各仓库 `origin/sit`）：`repo@sha`、…（表格或行内列举）
```

**版本块纪律**：需求每发新版（v0.2/v0.4…）→ 在头部追加一条 `V1.x 变更`，写清「版本对应关系 + ①新增/移除/改名清单」，并在相关章节做增量修订；不静默覆盖旧结论。

## 二、第 0 章：章节 ↔ 代码/文件对照总表

| 需求章节 | 功能点 | 前端文件 | 后端文件 | 数据库/表 |
|---|---|---|---|---|
| **4.1** 标题 | 一句话功能点 | 无则写 —（原因） | 类/服务名列表 | 表名/脚本名 |

要求：覆盖需求全部章节（含"不涉及开发"的章节，标注原因）；文件写**文件名**即可（完整路径留给各章与附录 D）。

## 三、第 0.1 节：关键流程 Mermaid

- 用 `flowchart TD`；按业务主线分组 `subgraph`（如"主线一：字段贯穿""主线二：规则管控"）。
- 节点内容三行内：**做什么 + 落在哪（表/接口/页面）+ 关键赋值**。
- 需求有版本变更时，在相关节点上标注 `（v0.x 新增/移除）`。
- 图只做导航，细节必须在正文；不出现与正文矛盾的节点。

## 四、第 0.2 节：全局设计约定（四张表）

1. **命名与码值表**：新字段的 DB 列名/前端控件名/接口字段名/标志位名，逐行给出类型与码值（如 `VARCHAR2(1)`，1=是 0=否，可空）。
2. **要素/枚举口径表**：需求术语 ↔ 代码码值的映射（如"赔付比例"= 字典 `benefittypenew` 30 = `EnumBenefitType.SELFPAYINSURANCE`），并写明"需求两章表述不同时各自按原文"的处理原则。
3. **业务码值表**：服务团队/状态/类型等关键码值（如 `SERVETEAM` 01=JV 02=中端 03=GHB），附代码证据位置。
4. **编码说明**：Java=GBK、Mapper XML/前端=UTF-8（以**本仓库实测**为准）；GBK 注释保持原编码、grep 加 `-a`。

## 五、章节结构（固定骨架 + 三种变体）

### 5.1 标准章节（有前后端改动）

```markdown
## 4.x <需求章节名>（需求 §4.x）

> **范围/口径说明**（可选）：本设计的边界、参照实现、术语映射、版本变更。

### 4.x.1 需求要点
| # | 规则 |      ← 原文规约逐条编号化（B1/C2/E1…），后续改造点挂这些编号

### 4.x.2 本章改动文件清单
| 项目 | 文件（相对仓库根） | 类型 |   ← 新增/修改；相对路径；行号勘误可在表后注明

### 4.x.3 后端改动
#### ① <改造点标题> —— `<文件/方法>`（修改，GBK/UTF-8）
> 定位：…
[代码块]
> 说明/注意/回归点

#### ② …

### 4.x.4 前端改动
#### ⑦ …

### 4.x.5 自测
1. 场景（造数条件 → 操作入口 → 期望落点/拦截文案）；2. …；最后一条固定"回归"。
```

### 5.2 变体 A：纯数据/脚本章节（无代码改动）
需求要点 → 现状结论（已核实证据）→ 改动文件清单（脚本）→ 脚本全文（含核对 SQL）→ 自测（脚本执行后页面/数据验证）。

### 5.3 变体 B：不涉及开发章节（如"验证场景"）
标题注明「—— 本需求不涉及开发」；原文条目逐条归属（落到哪章/哪个其他需求/为何不计）；给测试范围提示与基线/排期风险提示。

### 5.4 变体 C：跨服务章节（如权限控制）
按"现状结论（链路+码值+缺口）→ 改动文件清单 → 各服务改动（编号）→ 自测（含跨服务联调场景）"组织；跨团队/外部服务单列协作项。

## 六、代码块契约（核心，决定"开发能否直接复制粘贴"）

### 6.1 定位行格式

```
> 定位：`<项目>/<完整相对路径>`，<类名/方法名>（**当前 :起-止**，评估 :起 漂移 +N；固定行如 :2512 **无漂移**）。
```

- 必须给：当前行号范围 + 评估行号漂移；找不到时写"实际位置/命名变化"。
- 行号基准 = 文档头声明的基线；正文只引用当前基线行号。

### 6.2 代码块格式

```markdown
```java
2510				caseinfo += "&enterpriseFlag=" + enterpriseFlag;
2511				// <需求号>-<项目短名>-<描述≤10字>
2512				String tSpecialDeptJudge = "N";
2513				...
2514				System.out.println("调试日志：" + caseinfo);
```
```

规则：
- **未加注释的行 = 现有原文（前后各约 5 行）**；新增/修改行紧邻插入点，统一注释前缀：`// <需求号>-<项目短名>-<描述≤10字>`（XML 用 `<!-- -->`，SQL/properties 用 `--`）。
- 代码块内**带行号**（`行号<TAB>代码`），由 `scripts/extract_context.py` 生成；行号不复制进代码（开发按行号插入，粘贴时去掉行号列）。
- 语言标注：`java` / `xml` / `javascript` / `html` / `sql` / `properties`。
- **变换类改动**（把 A 改成 B）：先给原文块，再写 `改为：` + 新块；两块的锚点行必须可对应。
- **新增节**（整节新代码）：给 `> 新增文件：<路径>` + 完整文件（或完整类/方法），含 import 清单。
- 大段参照代码（如 300 行枚举/参考实现）不入正文，放 `references/` 或注明"参照 `<文件>:行号`，本次仅在其后追加 X 行"。

### 6.3 说明段（每个改造点后必写）

用 `>` 引用块写清：为什么改这里（链路位置）、易错点（如"此处是全列 update，漏改则标志落不了库"）、回归注意（哪些既有硬编码/联动不能动）、与先例的关系（参照哪个实现，差异是什么）。

## 七、附录模板

### 附录 A：SQL 清单汇总

| # | 脚本（gis-sql 相对路径） | 内容 | 章节 |
|---|---|---|---|
| 1 | `DDL/<日期>-all-ddl_<库>.sql`（新增） | 表/列/注释；核对语句 | 4.x① |

规则：DDL 与 DML 分文件；每个脚本给"内容 + 依据章节"；**归属他人的 DDL 写明"谁交付、是否先行、本需求只核对"**；已有列补齐按"执行前核对、已有则跳过"。

### 附录 B：接口/报文变更汇总

| # | 接口/报文 | 变更 | 方向 | 章节 |
|---|---|---|---|---|
| 1 | `<接口路径>` | 新增字段/key（值域） | A → B | 4.x③ |

规则：字段名/值域以**最新需求附件**为准；附件内部矛盾（如表格 Y/N vs 示例 1/0）不裁决，标"待确认"并保留两处出处；外部服务（聚合服务/厂商/契约）单列 SA/协作依赖。

### 附录 C：待确认 / 已定稿

- **C.1 待确认**：编号 + 事项 + 影响面 + 建议。凡影响联调/口径/边界的开放问题必列（需求附件矛盾、码值待核、范围待定、跨团队归属）。
- **C.2 已定稿**：编号 + 事项 + 采纳口径（含"已与谁确认/日期"）。评审中被用户拍板的结论从 C.1 **移入** C.2，C.1 留一行 `~~原条目~~ 已销项`。
- 撤销的方案：在相关章节保留一行「曾评估 X 方案，已撤销（原因）」；全文旧引用清零（grep 验证）。

### 附录 D：改动文件清单（按项目汇总）+ 上线顺序

```markdown
### D.1 总览
| 项目 | 新增文件 | 修改文件 | 小计 |   ← 与 D.2/D.3 逐项对账

> **不涉及仓库**：repo（原因）

### D.2 新增文件（N 个）
| # | 所属项目 | 文件路径 + 名称 | 说明 | 章节 |

### D.3 修改文件（M 个）
#### D.3.1 `<repo>`（x 个）
| # | 文件路径（相对 src/main/…） | 主要改动点 | 章节 |   ← 行号连续；每行标章节号

（D.3.x 按项目分小节）

### D.4 上线顺序建议
1. **DB 先行**：DDL 执行 + `user_tab_columns` 核对（含"已有则跳过"项、他人先行交付项与阻断条件）
2. **DML**：编码/规则配置脚本 + 缓存清理（如 Redis DICTTYPE）+ 页面验证
3. **服务发布**（无编译依赖可同批；接口变更均为新增字段=向后兼容）：顺序 + 依赖说明
4. **前端**：与后端同批
5. **验证顺序**：按章节走查
6. **回退**：DDL 可保留（可空列）/DML 停用方式/编码删除方式
```

### 可选增强（若有）
在正文对应章加「⑬（可选增强）」节，并在 D 附录加 `D.5 可选增强文件（N 个，不计入 D.1 总数）`——避免与必改项混淆。

## 九、交付前自检 12 项

1. 文档头：性质/需求来源（版本+修订）/不改范围/版本块/基线表齐全；版本块含本次变更。
2. 0 章总表覆盖全部需求章节（含"不涉及开发"章节）。
3. 0.1 Mermaid 与正文一致，含版本变更标注。
4. 0.2 四张表齐全（命名/码值口径/业务码值/编码说明）。
5. 每章 `需求要点→文件清单→后端→前端→自测` 结构在（变体章节按变体裁剪并注明原因）。
6. 每个改造点有定位行（当前行号+漂移）且**前后各约 5 行原文完整**。
7. 新增行注释前缀全文统一（grep 前缀计数 > 0，无旧前缀残留）。
8. 行号基准声明存在；正文行号与基线一致（抽查 5 个点）。
9. 附录 A/B/C/D 齐全；D.1 计数 == D.2 + D.3 实际行数（逐项目对账）。
10. C.1/C.2 分层正确；撤销方案留痕；旧方案引用零残留（grep 验证）。
11. 上线顺序含 DB→DML→服务→前端→验证→回退，且含他人先行 DDL 的阻断条件（如有）。
12. 自测节覆盖：正常/边界/只读或范围守卫/回归，每条"入口→操作→期望落点/文案"可执行。
