# req-detailed-design 需求详细设计

**输入**：需求文档（v0.x，可能多版本迭代，经 `req-doc2md` 转换）+ 改造点清单 `.md`（req-workload-estimate 产物，可选但推荐）+ 设计模板（默认使用本技能 `references/template-contract.md` 固化的 RCP-10910 式骨架）+ 多仓代码工作区（基线 `origin/sit`）
**输出**：`<需求号>-<需求名>-详细设计方案.md`（按需求章节、可粘贴级、含版本块）+ 支撑素材目录（并行核查产出）+ 交付摘要

与上下游技能的关系（链式调用，不重复造轮子）：

```
req-doc2md（需求文档 → md 包）──→ req-workload-estimate（改造点清单）──→ 本技能（详细设计文档）
                                                                     └→ 回放验证时对照既有设计文档
```

## 流程总览

```
阶段0 需求解析（req-doc2md + 样式/批注/版本diff/附件）
  → 阶段1 基线确认（origin/sit worktree + 漂移清单）
  → 阶段2 改造点承接与范围界定（章节映射/不改范围/继承待确认）
  → 阶段3 并行代码核查（多 agent 分派，产出"定位+前后5行"素材）
  → 阶段4 设计决策与跨参照复核（语义取证/参照实现/闭环验证）
  → 阶段5 文档撰写（按模板契约）
  →（评审循环：阶段6 反馈→查证→修订→版本块）→ 阶段7 交付与沉淀
```

**铁律：先核实基线（origin/sit）再动笔；每个改造点必须"定位 + 前后各约 5 行原代码"；全程只读代码，不改任何业务代码。**

## 硬规则（必须遵守）

1. 先出「改造点承接表 + 不改范围声明」给用户确认，再动笔写文档（对齐工作量评估的"先清单后定值"）。
2. 基线 = 各仓 `origin/sit` worktree；文档头声明基线表（repo@sha）；**所有行号以当前基线为准**，评估/他人行号一律视为待核。
3. 源码编码实测对待：**Java 多 GBK、Mapper XML 与前端多 UTF-8**；GBK 提取必须 `iconv -c`（不静默截断），grep GBK 文件必须加 `-a` 并交叉验证。
4. 每个改造点定位格式 = `项目 · 文件 · 类/方法 · 行号`，代码块带行号；行号漂移必须标注"评估行号→当前行号"。
5. 只读代码，不改代码；需求原文瑕疵（错别字/字段名不一致）保留原样加〔〕标注，不擅自修正。
6. 字段/码值语义必须查用法取证（DDL/DML/调用方/参照 SQL），**禁止想当然**（教训：`lcbill.premtype` 是账单层级不是首续期）。
7. 需求点名的参照 JIRA/既有实现必须**逐环节比对**（配置→传递→落库→清零→查询→展示），差异显式写明。
8. 新增标志/字段必须做闭环核对：置位→传递→持久化（含**全列 update 语句末尾**与 insert-select 显式列清单）→清零→查询→展示。
9. 多调用方/多副本必须逐一核对：因子清单的第二调用方、主表+日志表成对加列、双页面（普通/GHB）、双查询路径（含缓存分支）。
10. 未定口径进"待确认"、本设计采纳口径进"已定稿"，两栏分层；**撤销的方案留一行撤销说明**，不留死引用。
11. 版本纪律：需求每出新版 → diff → 增量更新设计 → 文档版本块记录（V1.x + 变更摘要 + 需求修订日期）；不静默覆盖旧结论。
12. 文档必含附录 A（SQL 清单）/B（接口报文变更）/C（待确认与已定稿）/D（改动文件清单 + 上线顺序），开发可独立执行。
13. 同一规则多消费方 → 抽公共方法/公共查询；附加能力必须失败隔离（不拖垮主流程，如保单列表查询不能被追缴 feign 拖垮）。
14. 外部服务 / 跨团队 / 非本工作区仓库（如接口聚合服务、契约服务）→ 列为协作项与待确认，不假设其行为。
15. 交付前跑 `references/template-contract.md` 的「交付前自检 12 项」，不通过不交付。

## 文档契约摘要

- 文档骨架、代码块格式、附录模板、版本块 → 写文档前**必读** `references/template-contract.md`。
- 每章固定结构：`4.x.1 需求要点（表格）→ 4.x.2 改动文件清单 → 4.x.3 后端改动（编号①②…）→ 4.x.4 前端改动 → 4.x.5 自测`；纯数据/无前端/不涉及开发的章节按模板变体裁剪，但保留标题并注明原因。
- 代码块：未加注释的行 = 现有原文（前后各约 5 行）；新增/修改行带统一前缀 `<需求号>-<项目短名>-<描述≤10字>`（Java/JS 用 `//`，XML 用 `<!-- -->`，SQL/properties 用 `--`）。
- 开头三件套：0 章总表（需求章节↔前端↔后端↔DB）、0.1 Mermaid 关键流程（含版本变更标注）、0.2 全局设计约定（命名/码值口径/编码说明）。

## 并行代码核查（阶段 3 摘要）

- 按业务分类分派 5-6 个并行 agent（如：接口+账单后端 / 账单+I类前端 / 福利树 / 理算 / 权限控制 / SQL 参照），每个 agent 的输出契约固定为：**文件路径、当前行号（含评估→当前漂移）、前后各 5 行转码后代码块、一句话语义、与评估清单不符之处**。
- agent prompt 必带四段：①worktree 绝对路径 + 编码实测结论 + `iconv -c` 提取命令；②改造点清单（路径/方法/评估行号/参照查询）；③输出契约；④素材文件路径（写盘，返回摘要即可）。
- **组长亲核清单**：元凶逻辑、公共方法签名、全列 update、跨服务调用链、SQL 口径——不信 agent 转述。
- 完整分派模板与失败处理 → `references/process.md` 阶段 3。

## 关键工具

- **`scripts/extract_context.py`**：按文件+锚点提取前后 N 行（自动 UTF-8→GBK 回退、带行号、可直接粘贴），支持 `--tasks tasks.json` 批量；**写代码块一律用它生成**，不手拼 `sed|iconv`（防编码截断与行号错位）。

```bash
python <skill_dir>/scripts/extract_context.py --file <path> --anchor "<方法名或原文片段>" [--before 5] [--after 5]
python <skill_dir>/scripts/extract_context.py --tasks tasks.json --out 素材.md
```

## 何时读 references

- **阶段 0-7 的完整动作、基线命令配方、agent 分派模板全文、评审循环与撤销留痕规范** → 读 `references/process.md`
- **写文档前（骨架/代码块/附录/版本块/自检清单/最小样例）** → 读 `references/template-contract.md`
- **遇到争议、踩坑、结果反常时** → 读 `references/pitfalls.md`（需求侧/代码侧/工具侧/协作侧共 18 条实战教训）

## 排查

| 现象 | 处理 |
|------|------|
| 中文注释乱码 / 行缺失 | GBK 文件未用 `iconv -c`；改用 `extract_context.py`（内置编码回退） |
| 锚点找不到 / 行号对不上 | 基线不是 origin/sit；先按阶段 1 配方更新 worktree，再按"类名+方法名+原文行"重定位 |
| Read/复制 docx 路径报不存在 | 文件名可能含 U+00A0 或全角空格；先 `ls -b` 看真实字节，复制到 `/tmp` 再处理 |
| 文档补丁被写坏（代码块缺字） | shell heredoc 里反引号被 bash 解释；用 `<<'PYEOF'` 或独立 .py 脚本 |
| 附录 D 文件数与正文清单不一致 | 写完后逐个 D.3.x 计数，与 D.1 总览对账（自检项） |
| 需求附件与正文矛盾（如值域 Y/N vs 1/0） | 不擅自统一，进"待确认"并写明两处出处 |
